自动化科研系统工作流总手册

这份网页手册面向真实运行中的 openclaw-research 系统，目标不是做营销式概览， 而是把当前系统到底如何工作、如何和 PaperNexus 联动、每个阶段用什么状态与产物控制质量、 以及为什么它能形成可恢复、可审计、可返工的自动化科研流水线，完整讲清楚。

当前系统的设计原则是：把“科研过程”拆成一系列有 owner、有 durable state、有证据制品、 有可回退控制的工作流阶段；把“图谱智能、文献发现、跨域机制桥接”等高密度研究智能尽量放到 PaperNexus 侧，把 openclaw-research 保持成 workflow engine、quality gate 和 artifact orchestrator。

1. 系统定位与边界

这套系统不是“一个会聊天的科研 Agent”，而是一套以项目目录为边界的科研 workflow engine。 它把科研过程拆成 durable state、受约束的角色分工、可重放的 runtime、可回退的阶段机、 以及由图谱证据和实验制品共同驱动的质量控制链。

系统最擅长什么

  • 把一个研究项目从 setup 自动推进到 write/submit 前。
  • 用明确的状态与制品约束返工、重跑、图刷新、写作修订和评审回压。
  • 把多 Agent 协作收束成 owner-based workflow，而不是自由漫游式聊天。
  • 把文献调研、图谱、实验账本、写作合同、评审压力包统一进同一项目目录。

系统不该承担什么

  • 不在本仓库内重实现 PaperNexus 的图谱算法、domain taxonomy、mechanism bridge 推理。
  • 不把所有跨域知识挖掘逻辑塞进 workflow-guard.ts 这种 facade 文件。
  • 不把写作质量寄托在 prompt 运气上，而是尽量转成 contract、artifact 和 gate。
  • 不把“审稿人可能会质疑什么”当作事后补丁，而是提前在 plan/write/review 中建模。

2. 总体架构

架构上，openclaw-research 被刻意分成“上游研究智能”和“下游流程控制”两层。 上游智能主要由 PaperNexus 提供，负责文献发现、知识图谱、challenge/insight/mechanism bridge packet；下游由 workflow runtime 负责，把这些 packet 变成项目中的可执行阶段、可见摘要和质量门槛。

PaperNexus 层

  • 文献发现、筛选、补料、全文获取。
  • 共享语料图与 graph presence 检查。
  • 跨域 mechanism bridge、challenge-insight、storyline packet。
  • 提供给 workflow 的上游事实源，而不是直接控制阶段推进。

Workflow 层

  • 阶段机、owner routing、回退与恢复。
  • 项目状态同步、mailbox、广播、auto iterator。
  • materializer：把图谱事实转成 ideation/story/review/writing contracts。
  • 把上传、refresh、rerun、queue 变成 workflow-owned 行为。

Agent / Skill 层

  • researcher：文献、图谱、创新、实验主控。
  • coder：代码改动与实验 bundle。
  • analyzer：claim-evidence、verdict、theory packet。
  • academic_writer 与 reviewer：故事线、写作、审稿、反驳。

为什么这样分层

因为高质量自动化科研最大的风险之一，是把“研究智能”和“流程约束”混在一处实现。那样会导致： 代码难维护、上下文难收敛、回归风险极高、系统很难稳定恢复。当前设计选择是： PaperNexus 负责产生更强的图谱事实与 packet，workflow 负责把这些事实变成可执行的科研控制链。

3. 端到端工作流

Stage Flow 阶段流

当前主阶段机是：setup -> graph_build -> frontier_mapping -> idea -> plan -> code -> experiment -> analyze -> review -> write -> submit -> done。 它不是线性 happy path，而是一个可以自动回退、自动补料、自动重入的阶段控制系统。

setup · owner = researcher
建立项目、onboarding contract、研究目标、baseline、metric、dataset、Zotero project path。
graph_build · owner = researcher
由 workflow-owned upload / discovery queue 驱动，进入 uploading -> verifying -> brainstorm_refresh 微阶段，确保图谱 ready。
frontier_mapping · owner = researcher
根据图谱、frontier files、anchor index、challenge/contradiction/transfer frontier 生成后续 ideation 的图基础。
idea · owner = researcher
运行 graph-first ideation contract 和 IDEA-CATALYST 子流水线，必要时发起 requisition，回退到 graph_build 补文献与图。
plan · owner = orchestrator
把 proposal、problem decomposition、idea-to-claim traceability 收束成实验计划与执行 budget。
code · owner = coder
按 experiment bundle 和 claim-to-experiment map 生成最小闭环实现，而不是开放式改代码。
experiment · owner = researcher
发起、监控、同步实验，必要时通过 /monitor-experiment 接管 remote run，跟踪 ledger、batch、plot pack 和 monitor cooldown。
analyze · owner = analyzer
把实验结果写回 claim-evidence matrix、track verdict、unsupported claims、theory packet。
review · owner = reviewer
生成 review pressure packet、reject-first、novelty attack、reverse outline、limitation audit。
write · owner = academic_writer
在 writing contract、paper story、reference bundle、fallback trigger、revision cycle 约束下撰写论文。
submit · owner = reviewer
做最终质量门槛检查、引用核验、外部审稿结果整合和人工 gate。
done
项目进入完成态，供后续 portfolio 轮转、多项目自治或历史经验沉淀使用。

自动推进是怎么发生的

  • 每次恢复、heartbeat、service coordinator pass 都会优先跑 research_workflow.auto_iterator_tick。
  • auto iterator 先检查状态缺口，再决定推进、回退、handoff、等待人工还是发起后台任务。
  • 如果阶段 owner 不是当前角色，它会优先做 mailbox/handoff，而不是“顺手继续做”。
  • 如果某个阶段产物 stale，它会先 materialize / rerun，而不是让 agent 靠上下文猜。

4. PaperNexus 联动流程

PaperNexus 现在不是一个“可选参考工具”，而是这套系统的上游研究智能来源。openclaw-research 已经通过 packet adapter 把 PaperNexus 的结构化输出接到 ideation、story、review 和 discovery rerun 上。

上游 packet 与下游消费关系

PaperNexus Packet 上游含义 openclaw-research 消费位置 作用
MECHANISM_BRIDGE_PACKET.json candidate/selected/pruned domains, bridge nodes, distance matrix, transfer bridges ideation_contract、idea_catalyst、Scout basis 让创新点搜索建立在跨域桥接事实之上，而不是本地 heuristics。
CHALLENGE_INSIGHT_PACKET.json challenge clusters、insight clusters、occupied zones ideation_contract、review pressure 控制“问题是否真实开放”“故事线是否真正回应 challenge”。
GRAPH_STORYLINE_PACKET.json task/challenge/insight/contribution/advantage/module motivations/evidence coverage writing_contract、graph_guided_writing、paper_story_state、review_pressure_packet 把图谱证据直接变成故事线骨架和写作约束。
LITERATURE_DISCOVERY_PACKET.json 需要补哪类论文、补完后该重入哪些阶段 paper_ingestion.queued_requests 与 stage preflight 让 discovery 变成 workflow-owned rerun，而不是 agent 口头建议。

联动控制链

  1. PaperNexus 产出 packet 文件到项目目录。
  2. materialize_papernexus_packet_contracts 把 packet 同步到现有 workflow contracts。
  3. stage preflight 在 idea/plan/review/write/submit 前优先跑 packet sync。
  4. 如果存在 discovery packet，workflow 会自动桥接成 paper_ingestion.queued_requests。
  5. auto iterator 看到 active discovery/import request 时，会回退到 graph_build。
  6. graph_build 完成上传、验证、graph refresh 后，系统再回到 frontier_mapping -> idea 或后续阶段。

典型 rerun 路线

review/write
  -> story gap or discovery packet detected
  -> queue literature discovery requisition
  -> graph_build / uploading
  -> graph_build / verifying
  -> frontier_mapping
  -> idea rerun
  -> plan / write / review continue

5. 文献调研质量控制

文献调研不是“搜到几篇论文”就结束。系统对文献调研的控制分成 discovery、ingestion、graph presence、 research memory、writing/review 补料五层。

5.1 如何控制找论文质量

  • 文献发现现在可以由上游 LITERATURE_DISCOVERY_PACKET 触发，而不是只靠 prompt improvisation。
  • packet 会声明 discovery_reason、target_domains、candidate_queries、required_stage_reentry。
  • 因此系统能回答：为什么需要补论文、该补哪类论文、补完后回到哪个阶段。
  • 这让“文献调研”成为 workflow 一部分，而不是上下文中的临时动作。

5.2 如何控制 ingest 质量

  • 论文上传已 workflow-owned，不再依赖 Researcher 随机创建子 agent 手动跑上传链。
  • paper_ingestion.queued_requests 记录 request id、status、trigger kind、batch manifest、repair target。
  • graph sync repair 会显式进入 repair contract，不再只是日志里的模糊失败。
  • completion broadcast、timeout、batch progress 都是 durable state。

5.3 如何防止“文献搜了，但系统没真正用上”

  • graph presence check 会验证 canonical papers 是否真正进入共享图谱。
  • graph_build 会阻止系统在图未 ready 时继续到 novelty-sensitive 阶段。
  • writing/review 阶段发现 story support gap 时，会自动触发 discovery rerun，而不是默默带着缺口继续写。
  • 跨周期 memory 会沉淀哪些 discovery 对 closing challenge 最有效，逐轮减少盲搜。

6. 图谱构建与验证质量控制

图谱构建是整套系统的中轴，因为后续 frontier mapping、idea catalyst、storyline packet、claim-evidence writing 都依赖它。系统对图谱质量的控制不是“图存在就行”，而是明确分成上传、验证、刷新和后续图契约。

graph_build / uploading

  • workflow 触发 PaperNexus import / batch submit / literature discovery requisition。
  • 只要 queue/batch 仍活动，就不会误推进到 frontier_mapping。
  • 避免“文献还没真正同步好，后面阶段就先跑了”。

graph_build / verifying

  • 通过 graph presence check 验证 expected paper 是否在共享图中。
  • 若 missing_papers + idle + active_batches=0，可进入 repair 模式。
  • 图 ready 是进入 frontier_mapping 的硬 gate。

graph_build / brainstorm_refresh

  • 图 ready 后刷新 brainstorm/storyline bundle，而不是要求手工 rebuild graph。
  • 这个微阶段只做“图就绪后的 reasoning refresh”，不做上游 PaperNexus 图算法。
  • 保证后续 ideation 建立在最新图事实之上。

为什么 graph_build 不再要求过早存在 brainstorm_cycle

因为 graph_build 的职责是把图谱事实准备好，而不是要求后续 reasoning contract 已经完整存在。 现在系统已经把这两者解耦：先保证图 ready，再刷新 brainstorm / storyline provider；这样图验证不再被过早的下游 contract 卡死。

7. 创新点与 IDEA-CATALYST 质量控制

当前创新点构建已经不是“读几篇论文后灵机一动”，而是 graph-first ideation contract + IDEA-CATALYST 子流水线的组合。它吸收了 EvoScientist 的强控制思路，但把高密度图谱智能更多交给 PaperNexus。

7.1 ideation_contract 在控制什么

  • GRAPH_IDEATION_PACKET.json
  • NOVELTY_TREE.md、CHALLENGE_INSIGHT_TREE.md、WELL_ESTABLISHED_SOLUTION_CHECK.md
  • CANDIDATE_POOL.json、RANKING_HISTORY.json、TOP3_DIRECTION_SUMMARY.md、RESEARCH_PROPOSAL.md
  • 这些文件把创新点从“想法”变成可比较、可淘汰、可沉淀的 durable artifacts。

7.2 IDEA-CATALYST 在控制什么

  • Decomposer：把问题拆成 domain-specific / domain-agnostic questions。
  • Translator：把 challenge 映射成可迁移的 mechanism hypothesis。
  • Scout：从 graph / mechanism bridge / domain distance 中筛选 source domains。
  • Gatekeeper：判断证据是否足够，否则发 requisition。
  • Integrator：把跨域桥接整合成 candidate idea fragments。
  • Judge：pairwise / Elo ranking，保留 top ideas。

7.3 质量控制点

控制点 当前机制 作用
候选池宽度 candidate_target_count = 15、hard_floor = 9 防止过早收敛，只看几个最顺手的方向。
occupied zone 检查 WELL_ESTABLISHED_SOLUTION_CHECK.md + challenge/insight packet 避免把已成熟赛道误当创新。
跨域桥接证据 bridge_evidence_tier、selected/pruned source domains 防止“跨域迁移”变成空洞口号。
证据不足回退 Gatekeeper requisition -> graph_build rerun 让补文献、补图成为系统动作，而不是人工补丁。
故事线可追溯 IDEA_TO_CLAIM_MAP.json 让 idea fragment 最终能压到 paper claim，而不是 ideation 和 writing 脱节。

8. 实验设计、代码与验证质量控制

很多自动化科研系统会在“有了创新点”之后迅速失控：计划不绑定 claim、代码不绑定实验、实验结果不回写故事。 当前系统的改造重点之一，就是把 plan -> code -> experiment -> analyze 这条链拉成事实约束链。

Plan

要求 proposal、problem decomposition、idea-to-claim traceability 已 ready，避免 planner 凭空编实验。

Code

通过 experiment bundle、baseline contract、validation contract 控制 coder 只实现当前需要验证的差异。

Experiment

用 ledger、remote run、monitor cooldown、sync status、plot pack 状态，把实验从“一次命令”升级成 durable runtime。

Analyze

Analyzer 必须产出 claim-evidence matrix、track verdict、unsupported claims、theory packet，后续写作与评审都消费这些结果。

这条链如何控制质量

  • 没有 baseline / validation contract，代码阶段不会放行。
  • 没有 experiment bundle 与 active innovation track 对齐，代码阶段不会放行。
  • 实验没跑完、远程 run 仍活动时，不会提前进入 analyze。
  • analyze 后的 unsupported / partial claims 会影响 review、write、discovery rerun。
  • proof appendix 是否强制，已按 proof_appendix_required 条件化，避免对纯 empirical 项目一刀切。

9. 论文写作与故事线质量控制

当前写作系统吸收了 EvoScientist 的一部分强约束，也吸收了 “2603.12226v1” 所强调的 story architecture 和 idea-catalyst 思路，但实现方式不是把所有写作智慧塞进 workflow guard，而是通过 writing contract、 paper story、reference bundles、fallback trigger、revision cycle、cross-cycle memory 来落地。

9.1 paper_story_state

  • STORY_SPINE.md
  • PIPELINE_FIGURE_SKETCH.md
  • MODULE_MOTIVATION_MAP.md
  • CLAIM_TO_EXPERIMENT_MAP.md
  • FALLBACK_NARRATIVE.md
  • REJECTION_RISK_TABLE.md

它相当于论文故事线的 durable backbone。当前已能直接消费上游 GRAPH_STORYLINE_PACKET，让 task/challenge/insight/contribution/advantage 更明确地建立在图谱事实之上。

9.2 writing_contract 与 writing support

  • section order、page budget、headline claim 上限、proof appendix、template mapping
  • WRITING_REFERENCE_BUNDLE.json
  • FALLBACK_ACTIVATION.json
  • PAPER_REVISION_STATE.json
  • FIGURE_ANCHOR_PLAN.md
  • CONTRIBUTION_TO_STORY_BRIDGE.md

这些产物把写作从“单轮生成”变成“有结构、可反复修订、可激活 fallback narrative 的过程”。

9.3 写作质量如何被系统控制

维度 控制机制 效果
故事线一致性 paper_story_state + KG_STORYLINE_PACKET.md 避免 introduction、method、experiments 各讲各的。
claim-evidence 对齐 IDEA_TO_CLAIM_MAP.json + CLAIM_TO_EXPERIMENT_MAP.md + claim support status 防止 headline claim 飘离实验事实。
fallback narrative 根据 unsupported/partial claims、review pressure 自动触发 当主故事撑不住时，不用等人工发现再大修。
revision cycle section pass、intro-method consistency pass、full-paper adversarial pass 把修稿变成 workflow，而不是一次性生成后结束。
figure-centric writing PIPELINE_FIGURE_SKETCH + FIGURE_ANCHOR_PLAN 让图成为故事骨架，而不是最后补图。

10. 审稿、反驳与跨周期学习

当前系统已经不把 review 理解成“最后看一眼”，而是把 reviewer pressure 提前到 review/write 之前， 并让 rebuttal、revision、cross-cycle memory 形成闭环。

review_pressure_packet

  • REJECT_FIRST_REVIEW.md
  • NOVELTY_ATTACK.md
  • UNSUPPORTED_CLAIM_AUDIT.md
  • REVERSE_OUTLINE.md
  • FIGURE_TABLE_QC.md
  • LIMITATION_AUDIT.md

review-response / rebuttal

  • 已有 rebuttal skill，不是从零开始。
  • 已加入更强的 champion strategy、issue color coding、fix-now vs defer 策略。
  • 让 rebuttal 不只是答复格式，而是策略性防守。

cross-cycle memory

  • IDE_CYCLE_MEMORY.json
  • IVE_CYCLE_MEMORY.json
  • ESE_CYCLE_MEMORY.json

它们不是新事实源，而是聚合层：总结哪些 idea 常赢、哪些 claim 经常 unsupported、 哪类故事线常被 reviewer 打穿、哪种 rebuttal 更有效。

为什么这很关键

如果没有跨周期学习，系统每一轮都会重新犯类似错误：重复追逐弱 novelty、重复写过宽故事、 重复做不够有说服力的实验。当前 memory 聚合层的目标，就是让系统跨 research cycle 累积“策略经验”， 而不是只累积原始文件。

12. 运行入口与观测面

当前最重要的交互入口是 Discord slash command、workflow tool 和 /workflow-status。 这三者一起构成“控制面 + 观测面”。

常见入口

  • /research-pipeline：创建或启动项目。
  • /project-init：补齐 onboarding contract。
  • /resume-pipeline：恢复当前项目。
  • /graph-build：触发 graph build / repair / refresh pass。
  • /workflow-status：查看当前真实状态。

在状态里能看到什么

  • 当前 stage / micro-stage / owner / next action
  • PaperNexus ingestion、repair、queued requests
  • Brainstorm contract 与 ideation contract
  • IDEA-CATALYST 状态、bridge 数、source domain 数、requisition 状态
  • KG storyline readiness、graph guided writing、auto discussion、auto gate review

如何判断系统是否真的在做高质量自动化科研

不要只看它会不会自动推进；要看它能不能在每个关键断点停住并给出正确的下一步：图未 ready 时不继续做 novelty-sensitive work， claim 不被支持时不直接写，story 撑不住时触发 fallback/discovery rerun，审稿压力过大时先缩 scope 或回退， 这些才是“高质量自动化科研”真正的标志。

本手册描述的是当前仓库中已经实现并接入 workflow 的真实系统行为。它刻意强调“控制链、状态文件、上游 packet、质量门槛”的关系， 目的是让读者在脱离聊天上下文后，仍能理解为什么这套系统可以持续运行、恢复、返工并逐步逼近高质量科研产出。
